## ① CSV 列27「NC名」

- ヘッダ末尾に `NC名` を追加（26列 → 27列。既存26列の順序・内容は変えない）。
- 値は `j.raw`（NC ファイルの基底名。パスと `.iso` を含まない。例 `260618_TiA_10T_w1_b1_20260706_1014`）。無ければ空。`csvCell` でクォートする（`,` は含まないはずだが統一のため）。
- `raw` は v0.11 の dedup キーでもあるため、ジョブごとに一意（同じ `raw` は登録時にスキップされる）。手書き行（校正等）は本人が付けた名前がそのまま入る。
- 患者名は NC ファイル名に含まれない（hyperDENT のジョブ名とは別）。本列の追加で CSV の個人情報の範囲は変わらない。

## ② 状態 `部分`

**定義**: 突合できた（`mt` が null でない）行のうち、**期待バーのうち消費できた種類の数が `E.length` 未満**の行。`推定`（期待バー不明）には付けない（E が無いので「一巡」が定義できない）。

```
const full = mt && !mt.estimated && Object.keys(mt.used).length >= E.length;
if(mt && !mt.estimated && !full) tags.push("部分");
```

- 付ける位置: 突合状態（`ok` / `救済` / `尻尾`）の**後ろ**、`全N欠` の**前**。`ok` は消さない（例 `ok+部分`、`救済+部分`、`救済+尻尾+部分` はあり得ないが機械的に許容）。
- 典型例: 日末のジョブで 11→12 まで消費し 16 の出番が翌朝（`役割3秒` が空）。NC出力後に中止したジョブ。`ok` のままだと予測 vs 実測の突合で「速かった」ように見える。
- 画面（`renderJobs`）の実消費欄にも `(部分)` を付ける（`(尻尾)` `(推定)` と同じ位置、`救済` バッジの前）。
- `used` のキー数で判定する理由: `picked` は尻尾で同じバーが2回入るため本数では数えられない。`used` はバー番号ごとに合算済みなので種類数＝消費できた役割数。
- 拾えないケース（仕様として承知の上）: 折損→交換→同じ NC を途中再開した行は、3役割とも時間があるので `ok` のまま（design-doc §7 未決8）。

## ③ ブロック NC名の日付フォールバック

**現状（v0.13.3）**: `parseNcPath` は

```
const tm = base.match(/_(\d{8})_(\d{4})$/) || base.match(/_(\d{4})$/);
if(tm){ r.hhmm = tm[tm.length-1]; if(tm.length===3) r.ymd = tm[1]; }
```

で、ディスクの `…_w1_b1_20260706_1014` は日付が取れるが、ブロックの `165238430520261102_1556`（数字列に日付が直結、`_` が無い）は2番目の形に落ちて **`hhmm` だけ取れ `ymd` が無い** → 加工日が UI の日付になる。翌日以降に貼るとその行だけ日付がずれ、突合も外れる（2026-11-02 の w1 ブロック Br で確認。当日貼りだったので実害なし）。

**変更**: 2番目の候補として `_` 無しの末尾形を足す。**日付の妥当性検査を付ける**（ブロック名は任意の数字列なので、偶然 `12345678_1556` のような形でも暦日として成立しないものは採用しない）。

```
function ymdOk(s){                       // YYYYMMDD が暦日として妥当か（2020〜2099年、月01〜12、日01〜31）
  const y=+s.slice(0,4), m=+s.slice(4,6), d=+s.slice(6,8);
  return y>=2020 && y<=2099 && m>=1 && m<=12 && d>=1 && d<=31;
}
const tm = base.match(/_(\d{8})_(\d{4})$/)
        || base.match(/(\d{8})_(\d{4})$/)   // ③ ブロック: 数字列の末尾8桁＋_HHMM
        || base.match(/_(\d{4})$/);
if(tm){
  r.hhmm = tm[tm.length-1];
  if(tm.length===3 && ymdOk(tm[1])) r.ymd = tm[1];
}
```

- 1番目（ディスク形）の挙動は変えない。妥当性検査は1番目にも掛かるが、hyperDENT が書く日付は常に暦日なので実質無影響（念のため T36-2 で固定）。
- 「日付が取れたら `ymd` 優先、無ければ UI 日付」という登録側の規則（v0.10）はそのまま。`isBlock` 判定（英字なし）も変えない。
- **登録済みのブロックジョブには遡及しない**（パース結果は保存時固定）。受け入れ確認で日付が怪しい既存行があれば、削除→再貼り付けで直す（design-doc §5）。
- note-format.md r2 §6「日付は NC名の8桁（無ければ貼り付け時の UI 日付）」はこのままで正しい（8桁を読む形が広がっただけ）。改訂不要。

  - T36-3 `12345678_1556.iso`（暦日でない）→ `ymd` が無い（undefined）、`hhmm === "1556"`
  - T36-4 `1655_1556.iso`（8桁が無い）→ `ymd` が無い、`hhmm === "1556"`
  - T36-5 登録経路: UI 日付 2026-11-05 でブロック行を貼ったジョブの `date` が `2026-11-02` になる（UI 日付に落ちない）。登録関数が `__app` から呼べなければ `parseNcPath` の `ymd` で代替し、その旨を §7 に書く
- 既存テストで `状態` の完全一致を見ているもの（T28-1 の `ok`、T29-5 の `救済+尻尾` 等）が、フィクスチャの行が一巡している限り変わらないことを確認する。**9/7 d1 フィクスチャの #12（11,12 のみ）は `ok+部分` に変わる**ので、該当する既存の期待値があれば更新する（T28-1 は時刻 17:42 の行を見ていないはずだが要確認）。
- 既存フィクスチャに `_` 無しのブロック名があれば、③で日付が変わり突合結果が変わりうる。変わった行は完了報告に列挙する。

変異テスト（推奨）: `部分` の判定を `>=` から `>` に壊す→T35-2 が落ちる／`!mt.estimated` を外す→T35-4 が落ちる／列27を外す→T34-1 が落ちる／③の2番目の候補を外す→T36-1 が落ちる／`ymdOk` を常に true にする→T36-3 が落ちる。

## 3. 受け入れ確認（実機）

0. 先に JSON バックアップ（§6ルール5）。
1. 加工記録 CSV のヘッダ末尾が `…,歯数(算出),裂溝,NC名`。NC名列の値が `.iso` 行の基底名と一致する。
2. 9/7 d1 17:42 #12 の行（11,12 のみ）の状態が `ok+部分`。同日 13:13 #25 は `ok` のまま。
3. 画面で同じ行に `(部分)` が出る。
4. Excel で `部分` を含む行を除外しても、件数・歯数の集計（状態に依らない列）は変わらない。
5. ③: UI の日付を**今日以外**にしてブロック行（例 11/02 の `165238430520261102_1556.iso` 行。既に登録済みなら dedup で弾かれるので、先に削除するか別のブロック行で）を貼り、プレビューの日付が NC名の日付になる。加工記録の既存ブロック行で日付が貼り付け日とずれているものがあれば、削除→再貼り付け。
