## 0. 背景（なぜこの5点か）

2026-09-08 の実データ検証で判明した3つの事実:

1. **取込の途中終了が無言で起きる**: 取込は SST 上の Measure ログのコピー**全部**（d1だけで31本×10MB）を毎回読み直すため数分かかり、途中で離れても取込ログは最後に一括表示されるので痕跡が残らない（9/7 の d1/d2 セグメント欠落の真因）。
2. **突合の連鎖ズレ**: 1件のジョブが null になると、その孤児セグメントが次ジョブの窓に残り、集合型（順序不問）の一巡判定がそれを食う。9/7 d1 では支台ジョブ全件で「バー16が1つ前のジョブの仕上げ分」という1件ズレが夕方まで連鎖し、最後のジョブが枯渇で null になった。long_inside の尻尾セグメント（66→67→69→**短い67**）問題も同じ機構。
3. **SEG_EPOCH 固定は時限爆弾**: 2026-07-01 以降を全保持する設計のため、d系（1日100本級）の蓄積で再び 5MB 上限に当たる。

## ① 取込: Measure ログは最新1本のみ

**根拠**: Measure ログは追記型。古いコピーは最新コピーの部分集合なので読む必要がない。

**仕様**
- `logs` を `machineFromPath` でマシン別にグループ化し、各マシンで **`lastModified` が最大の1本**だけを処理する。同値なら `size` が最大のものを第2キーとする。
- 処理しなかった本数はマシンごとに**1行にまとめて**ログする:
  `スキップ: d1 Measureログ 30本（古いコピー。最新1本のみ処理）`
  ※ 31行の羅列は出さない。
- マシン判定不可のファイルは従来通り個別にスキップ行を出す。
- INI の処理は変更しない（全本を lastModified 昇順で処理し ±2分 dedup。交換検知の連鎖に必要）。

## ② 取込の進捗表示・二重起動防止

**仕様**
- 取込開始時に `btnDir` を `disabled` にし、完了（または例外）で戻す。
- `dirLog` の先頭に進捗行を置き、ファイル1本処理するごとに更新する:
  `処理中… INI 12/31 ／ Measure 1/4`
  各ファイルの処理後に `await new Promise(r=>setTimeout(r,0))` を挟み、ブラウザに描画機会を与える（これがないと進捗が見えない）。
- 完了時、末尾に `完了: INI n件処理 ／ Measure m件処理 ／ 所要 s秒` を出す。
- 例外は従来通り `エラー:` 行（v0.12 の無言死禁止を維持）。

## ③ セグメントのローリング保持

**仕様**
- `SEG_EPOCH` 定数を廃止し、`const SEG_KEEP_DAYS = 90;` と `function segCutoff(){ /* today - SEG_KEEP_DAYS を "YYYY-MM-DD" で返す */ }` を追加する。
- `loadDB` の filter と、取込時の `if(s.a < SEG_EPOCH)` の両方を `segCutoff()` に置き換える。取込ログの文言も `…以前の N件は保持期間外` に変更。
- `renderJobs` で、ジョブの `date` が `segCutoff()` より前なら実消費欄に `—（保持期間外）` と表示する（null と区別する）。

**設計判断のメモ**: バー寿命の集計は交換履歴（finalRun）と INI の RunTime から出るため、古いセグメントを落としても失わない。利益率 Level1 も交換CSV×単価（バー単位）なのでセグメントに依存しない。

## ④ バー交換理由の記録

**仕様**
- `db.exchanges[]` の各要素に `reason: string|null` と `memo: string|null` を追加（既存レコードは undefined 扱い＝未記入）。
- 理由の選択肢（固定）: `段取り` / `寿命(切削面)` / `脱落` / `折損` / `異音` / `傷(品質)` / `その他`。
- `renderExchanges` の表に「理由」列を追加。セルは `<select>`（先頭に空＝未記入）で、`onchange` で即保存（`saveDB` → 再描画不要、値だけ更新）。メモは「メモ」ボタン → `prompt()` で入力（既存の `editExchange` と同じ流儀）。メモありは行末に `📝` を付ける程度で十分。
- 交換CSV に `理由,メモ` の2列を末尾に追加（メモ内の `,` と改行はダブルクォートで囲む）。
- 交換検知直後（INI 貼り付け／取込で `交換検知N件`）に理由入力を強制はしない。後から表で埋める運用。

## ⑤ 突合: 順序型 ＋ 2パス ＋ 尻尾許容

### 現行（v0.12）の問題点
`matchSegments` は期待バーを `Set` で持ち、窓の先頭から「期待外→打ち切り／再登場→打ち切り」で集合が一巡するまで消費する。**順序を見ない**ため、前ジョブの孤児（例: 仕上げバー16）が窓の先頭にあると自分のものとして食ってしまう。

### 新仕様

`expectedBars` は**順序付き配列 E**（荒→中→仕上）として扱う。`matchSegments` は「1パス目」用と「2パス目」用の2モードを持つ（引数 `mode`）。

**共通の前処理**（現行のまま）: マシン一致、`a >= start` で抽出、時刻昇順、隣接同一スロット統合（≤2分）、12h超セグメント（PARK）はスキップ。

**1パス目（順次消費・順序型）** — `renderJobs` のカーソル付きループで従来通り呼ぶ
```
k = 0                          // 次に期待するインデックス
for seg in mseg:
  bar = barOf(seg)
  if k == 0:                   // まだ何も消費していない
    if bar == E[0]: consume; k=1; continue
    if bar in E:  continue     // ← 新規: 同系の孤児（前ジョブの残り）は飛ばす
    break                      // 期待外＝別ジョブが始まっている → null
  else:
    if bar == E[k]: consume; k++
       if k == len(E): 尻尾判定へ（下記）; break
       continue
    break                      // 順序違い・再登場・期待外はすべて打ち切り
```
**尻尾許容**（一巡完了直後のみ）: 次のセグメントが `bar == E[1]`（そのテンプレの2mmバー）かつ **保持時間 ≤ 10分** なら追加で消費する（long_inside の内面仕上げ）。それ以外は消費しない。尻尾を食ったときは `picked` に `tail:true` を付ける。
`lastEnd` は消費した最後のセグメントの `b`（尻尾込み）。

**2パス目（孤児救済）** — `renderJobs` で1パス目を全ジョブに回した後、null だったジョブに対して NC 順に実行
- 1パス目で誰かに消費されたセグメントの集合 `consumed`（`machine+a` をキー）を `renderJobs` 側で保持し、2パス目には**未消費セグメントだけ**を渡す。
- 探索範囲: `a > base`（ジョブの NC 時刻。カーソルは使わない）かつ `a < base + 24h`。
- 未消費セグメントを時刻順に見て、最初の `bar == E[0]` から順序型で消費（1パス目と同じ順序ルール、尻尾許容も同じ）。途中で順序が崩れたら打ち切り。
- 2パス目で拾えたジョブは実消費欄に `救済` バッジを付けて表示する（ユーザーが「NC順と加工順が入れ替わった」と分かるように）。

**表示**: 実消費の文字列は従来通り `11=00:06:41 / 12=… / 16=…`。尻尾を含む場合は同バーに合算し、`(尻尾)` を末尾に添える。

### 検証用フィクスチャ（実データ: 2026-09-07 d1）
支台ジョブの期待バー E = [11,12,16]、クラウンの E = [50,51,52]。ジョブ（NC時刻）: #27 11:34 支台 ／ #25 11:40 冠 ／ #45 11:45 冠 ／ #16 11:48 冠 ／ #25 13:13 支台 ／ #44 13:38 支台 ／ #37 13:42 支台 ／ #16 14:20 支台 ／ #14 14:25 支台 ／ #47 16:39 支台 ／ #11 16:49 支台 ／ #12 17:42 支台 ／ #45 17:44 支台。

**期待結果**

## ⑥ 同梱の小修正（long_inside 関連）

1. `KIND` のマッチ（L358）: `s.includes(k)` のフォールバックは **`石支台` のみ**に限定し、ASCII キー（Cr/In/On/Br/Con）は `\b` 一致だけにする。（現状 "Inside" が `includes("In")` に当たりインレー誤検出）
2. templateName ホワイトリスト（L384）に `s.match(/\b(long_inside)\b/i)` を追加。取得した値はそのまま `templateName` に入れる（辞書は持たない方針を維持）。
